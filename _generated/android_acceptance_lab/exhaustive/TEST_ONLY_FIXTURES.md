# TEST_ONLY Fixtures — Attempt & Honest Architectural Finding

## Что сделано
Засеяны TEST_ONLY фикстуры в production owner_center store (no-send): 4 события (P0-P3),
5 уведомлений, 1 инцидент, 1 решение. Canonical lead store (rev 254) НЕ трогался. Затем удалены.

## Критическая находка (почему фикстуры НЕ разблокируют контролы)

Приложение **намеренно фильтрует test_only данные** из production-представлений: Android НЕ
шлёт `includeTest=true` ни на одном эндпоинте (`/notifications`, `/incidents`, `/owner-decisions`).
Это by-design safety: реальный владелец никогда не должен видеть тестовые данные в проде.

Проверено: с засеянными фикстурами app-view (без includeTest) показывает
notifications=0, incidents=0, decisions=0 — фикстуры **невидимы UI приложения**.

## Следствие (честное противоречие в требованиях)

Спецификация требует тестировать data-gated контролы через TEST_ONLY фикстуры, НО приложение
(корректно) скрывает test_only из production-вьюх. Сделать эти контролы видимыми в UI можно только:
1. Засеять НЕ-тестовые (реальные) данные — нарушает «не менять реальные лиды», портит canonical/KPI.
2. Добавить в release debug-флаг include-test — рантайм-изменение, встраивающее видимость тестовых
   данных в боевую сборку (рискованно и меняет тестируемое поведение).

Ни один вариант не безопасен. Поэтому фикстуры удалены (store очищен, canonical не тронут).

## Вывод
Data-gated контролы списков/деталей/диалогов (≈139 из 187 UNEXECUTED) НЕ могут быть выполнены
индивидуально без либо порчи production-данных, либо изменения safety-поведения приложения.
Это архитектурный предел, а не недоработка харнесса. Реально достижимый потолок индивидуального
выполнения на сопряжённом проде без порчи данных: ~94-130 из 283 (статические/навигационные/
toggle/dangerous-gate контролы), что и зафиксировано в ledger RUN_1.
